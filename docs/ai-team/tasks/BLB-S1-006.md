## Objective

Port Belimbing `app/Core/User` (migration prefix `0200_01_20_*`) as the
`core/user` deep module: five tables — `users`, `password_reset_tokens`,
`user_pins`, `user_database_queries`, `notifications` — with schema
contract, public API, and focused tests.

## Evidence and context

Canonical points verified by the implementer against Belimbing at
`e70b4d33c0b10790e681f4c2b5095d85a53bc918` and ratified by the steward:

1. `users` has no `tenant_id` and no soft deletes; tenancy derives through
   the nullable `company_id` (`app/Core/User/Livewire/Users/Index.php:110-111`
   left-joins `companies` and filters `companies.tenant_id`, which removes
   null-`company_id` users from tenant-scoped lists).
2. End-state `users` has no `prefs` column
   (`0200_01_20_000007_migrate_user_preferences_to_settings.php` moved it to
   `base_settings`); do not resurrect it.
3. `notifications.id` is a UUID primary key
   (`0200_01_20_000005_create_notifications_table.php:23`); Laravel assigns
   `Str::orderedUuid()` client-side.
4. `user_pins.url_hash` is `char(32)`
   (`0200_01_20_000003_create_user_pins_table.php`).
5. `company_external_accesses.user_id` (column, index, FK, `:nilify_all`)
   is added by this module's migration `0200_01_20_000002`, satisfying the
   Company contract's existing `core/user external-access owner` optional
   group. The earlier deferral was withdrawn by the implementer; the group
   must land complete (column + index + FK) because
   `SchemaVerifier.compare_optional_groups/4` errors on partial groups.

## In scope

- The five tables, their schema contract, and the `optional_groups`
  completion above.
- A public API taking an **already-hashed** credential and rejecting any
  value not in crypt (`$2y$…`) format — Belimbing stores Laravel bcrypt.
- `user_pins` / `user_database_queries` schema only; their behavior belongs
  to S3 (Menu / Base Database query surface).

## Out of scope

- Credential hashing and any hashing dependency (`mix.lock` stays
  unclaimed). Registration, login, and password reset are S2.
  **Ratified by the user**, recorded by claude/opus-5 2026-08-12T20:52+08.
- Employee or Company module edits.

## Handoff

- **Changed paths:** `apps/core/user/**` only. No shared file, no `mix.lock`,
  no other module.
- **Public contract:** `list_company_users/2`, `get_user/3`, `create_user/3`,
  `update_user/4`, `delete_user/3`, `notifiable_identity/0`. All take a
  `%Scope{}` and return `Summary` structs; schemas, queries, and the stored
  credential stay private.
- **Compatibility impact:** creates `users`, `password_reset_tokens`,
  `user_pins`, `user_database_queries`, `notifications`, and completes Core
  Company's `core/user external-access owner` optional group — column, index,
  and foreign key in one migration, since the verifier treats a partly-present
  group as an incomplete contribution.
- **Canonical points preserved:** no `tenant_id` and no soft delete on `users`;
  nullable `company_id`; `notifications.id` is `uuid`; `user_pins.url_hash` is
  `char(32)`; `users.prefs` stays dropped per `0200_01_20_000007`.
- **Known limitations / deferred work:**
  - No tenant-wide user list. Belimbing's primary read left-joins `companies`
    and filters `companies.tenant_id`; reproducing it needs a Core Company
    public function returning the scope's company IDs as a composable
    subquery. Raised as a Company API request rather than crossing the
    boundary. This is the gap most likely to matter to Web later.
  - `user_pins` and `user_database_queries` have schema but no public API;
    their behavior belongs to Menu and Base Database in S3.
  - No hashing. Writes take an already-hashed `:password_hash` and reject
    non-crypt-format values, per the user's decision. Registration, login,
    reset, and verification are S2.
  - Compatibility verification against a real migrated database has not run
    here; that is BLB-S1-009's fresh-schema replay.
- **Suggested reviewer:** anyone other than me. Highest-value targets: the
  per-company read as a substitute for Belimbing's tenant-wide list, and
  whether rejecting non-crypt-format credentials is the right guard or an
  over-reach.
