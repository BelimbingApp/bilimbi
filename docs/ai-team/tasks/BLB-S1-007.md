## Objective

Extend `Bilimbi.Base.Database.SchemaVerifier.type_matches?/2` so schema
contracts can express the four PostgreSQL column types Belimbing's
Base/Core schema requires: `:uuid`, `{:char, n}`, `:jsonb`, `:inet`.

## Evidence and context

`type_matches?/2` currently has eleven clauses
(`{:varchar, n}`, `{:timestamp, n}`, `{:numeric, p, s}`, `:bigint`,
`:boolean`, `:date`, `:double_precision`, `:integer`, `:json`, `:smallint`,
`:text`) and no catch-all, so a contract naming an unknown type raises
`FunctionClauseError` instead of reporting drift. Belimbing usage,
confirmed by the implementer against Laravel `PostgresGrammar.php`
(`laravel/framework ^13.14.0`):

- `uuid` — `notifications.id` (`app/Core/User`, `0200_01_20_000005:23`);
  Core User critical path;
- `char(n)` — `user_pins.url_hash` is `char(32)` (`0200_01_20_000003`);
  Core User critical path;
- `jsonb`, `inet` (`ipAddress()`) — required by Base Audit in S2; added now
  to avoid reopening this file.

## Handoff

- **Changed paths:** `apps/base/database/lib/database/schema_verifier.ex`,
  `apps/base/database/test/schema_verifier_test.exs`. Nothing else. `mix.lock`
  untouched.
- **Public contract:** `SchemaVerifier.column_spec()` now admits `{:char, n}`
  alongside the existing tuple types, and `type_matches?/2` models `:uuid`,
  `{:char, n}`, `:jsonb`, and `:inet`. Purely additive — no existing contract
  changes meaning, which is why the eight tests include the five originals
  unmodified.
- **Catch-all decision: report drift, do not raise.** The closing clause is
  `defp type_matches?(_expected, _actual), do: false`, mirroring the clause
  `default_matches?/2` already ends with. An unmodelled contract type now
  surfaces as `"<table>.<column>: incompatible type"` instead of crashing the
  verify run. Covered by `"reports an unmodelled contract type instead of
  raising"`. A verifier whose job is reporting drift should not be the thing
  that explodes on an input it does not recognise; the symmetry with
  `default_matches?/2` decided the style.
- **Compatibility impact:** None to any database. This changes what a contract
  can *say*, not what any schema *is*. No migration, no schema contract, and no
  table is touched.
- **Test approach:** a `gadgets` temporary table carrying real `uuid`,
  `char(32)`, `jsonb`, and `inet` columns, so the clauses are checked against
  what `information_schema` actually reports rather than against an assumed
  string. Three tests: exact match, drift on all four (each swapped for the
  type a careless port would reach for — `:bigint` for uuid, `{:char, 16}` for
  `char(32)`, `:json` for `jsonb`, `{:varchar, 45}` for `inet`), and the
  unmodelled-type case.
- **Validation:** as above. `mix precommit` deliberately not run.
- **Known limitations / deferred work:**
  - `:inet` and `:jsonb` have no consumer yet. They are Base Audit's (S2). I
    added them on the argument in the card, but a reviewer may reasonably hold
    that unused vocabulary should wait for its module; I would not argue hard
    against reverting those two.
  - The four types are matched by name only. `char(n)` checks length, but no
    clause checks collation, domain types, or arrays. Nothing in Belimbing's
    Base/Core schema needs those.
  - `ulid` (Core/AI, S4) is `char(26)` and is therefore already covered — I did
    not add a distinct `:ulid` spelling, because the stored type genuinely is
    `character(26)` and inventing a synonym would hide that.
- **Suggested reviewer:** anyone other than me, and please treat this as more
  than a rubber stamp. The card itself notes that this concentrates shared
  foundation code and its first consumer (`BLB-S1-006`) in one agent's hands —
  that was the tradeoff I flagged when the user chose option (a). The clause I
  would scrutinise first is the catch-all, since it converts a loud failure
  into a quiet reported one.
