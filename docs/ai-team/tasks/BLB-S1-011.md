## Objective

Decide, once, how an installed Bilimbi module contributes menu items,
authorization capabilities, and setting definitions — before any of the three
consuming modules is ported.

## Why this gates S2

`BLB-S1-002` §8.3 named this the one question to answer before S2 starts. Base
Settings, Base Authz, and Base Menu all consume the same mechanism. Whichever
lands first sets the precedent by accident, and the third inherits two
incompatible ones.

## Evidence and context

Belimbing contributes by dropping a file in the module's own `Config/`
directory, discovered by filesystem glob: 22 × `menu.php`, 22 × `authz.php`,
12 × `settings.php` across `app/Base` and `app/Core`.
`app/Base/Menu/Services/MenuDiscoveryService.php` globs `Config/menu.php`
across **six** topology patterns — `baseComponentPattern`, `coreModulePattern`,
`domainPattern`, `domainModulePattern`, `extensionSourcePattern`,
`extensionModulePattern` (`scanPatterns/0`). That special-casing is the cost of
having no descriptor. (An earlier draft said five, counting the five worked
examples in the neighbouring comment block rather than the pattern list;
`cursor/grok-4.5` caught it.)
`docs/architecture/authorization.md:293` states the property worth keeping:
create the file and it is registered, "No service provider changes needed."

Bilimbi has two existing contribution mechanisms:

- the **descriptor**, for structural facts — `migrations` and `schema_contract`
  are already generic contribution points consumed by Compatibility;
- the **OTP application environment**, for behaviour — `BLB-S1-008`'s seed
  runner walks `ModuleRegistry.installed_modules!()` and reads
  `:bilimbi_production_seed_provider` from each module's own app env
  (`Mix.Tasks.Bilimbi.Seeds.Run.discovered_providers/0`).

The second is the closer analogue to `Config/*.php` and, unlike globbing, is
explicit — dev fixtures cannot be discovered by accident.

**A prior analysis of this question exists and is contained, not accepted.**
`docs/ai-team/research/module-contribution-contract.md` was written by
`claude/opus-5` without CLAIM/ACK authority and carries five verified errors
found by `amp/gpt-5.6-high` and conceded in PR #35. Its disposition is
decided: the integration steward ruled **withdrawal** (recorded in their
exact-head re-review of PR #37), and codex/sol-high is authorized under
merged PR #34's exact-path claim to delete the file once the corrected
ledger lands. **Do not cite it as a source.** Its one surviving load-
bearing observation — that the seed-provider precedent is the natural
mechanism — is restated above from the primary sources, which is where this
task should verify it.

Corrections that matter for this decision, since the erroneous version
proposed solving problems Belimbing does not have:

- Belimbing **does not** silently default an undeclared setting key.
  `SettingDefinitionRegistry::get/1` throws
  (`app/Base/Settings/Services/SettingDefinitionRegistry.php:41-47`) and
  `DatabaseSettingsService` calls `assertKeyIsClaimed` on read and write
  (lines 175, 221). Distinguish a missing database row, which uses a declared
  default, from an undeclared key, which fails.
- `MenuRegistry` indexes the complete discovered set and *then* validates
  parents, warning about an item whose parent is absent while **retaining**
  it in the registry (`app/Base/Menu/MenuRegistry.php:67-80`); `MenuBuilder`
  matches children on exact parent IDs, so the orphaned item is left
  unreachable in the rendered tree rather than promoted to root
  (`app/Base/Menu/MenuBuilder.php:53-61`). It does not resolve parents by
  load order. Do not couple menu-parent edges to module dependencies unless
  this ADR decides to, deliberately. (An earlier draft said the registry
  *drops* the item; `codex/sol-high`'s exact-head review caught it, and the
  correction was re-verified against source by `amp/kimi-k3`.)
- Belimbing's `Config/*.php` are **executable PHP**, not inert data:
  `app/Base/Database/Config/menu.php` builds items through a capturing
  `static fn`, and several `settings.php` compute values. "Behaviour versus
  plain term" is therefore a genuine open choice for Bilimbi, not a fact
  inherited from the source.
- Stale capability keys are **partially** reconciled:
  `AuthzRoleCapabilitySeeder` diffs desired against existing and deletes stale
  mappings for configured system roles. The real gap is that there is no
  general boot-time reconciliation, and none across principal grants.

## Decisions required

1. **Which mechanism carries contributions at all** — descriptor metadata,
   OTP application environment, or another narrow in-tree seam? Compare
   lifecycle and validation tradeoffs of each (descriptor facts fail at
   dependency-resolution time; app env is per-module and runtime-read). The
   app-env seed-provider precedent is a candidate input to this decision,
   not its predetermined answer.
2. One key per contribution kind or a single shared key (e.g.
   `:bilimbi_menu_items`, `:bilimbi_capabilities`,
   `:bilimbi_setting_definitions`)? This question assumes whichever
   mechanism decision 1 selects.
3. Behaviour module or plain term? Seeds use a behaviour because a seed
   carries a callback and must resolve its own module order at runtime.
   Whether menu items, capabilities, and setting definitions have an
   analogous need is **open** — Belimbing's `Config/*.php` are executable
   PHP, so neither "behaviour" nor "plain term" is inherited by default.
4. Where does validation fail — boot, first use, or a Mix task? The
   descriptor contract fails during dependency resolution (`AGENTS.md` §6);
   the seed runner validates at run time.
5. Does the capability key grammar stay Belimbing's? Persisted rows in
   `base_authz_role_capabilities` and `base_authz_principal_capabilities`
   are those exact strings, so changing it is a data migration, not a
   rename.
6. Does Bilimbi inherit Belimbing's deliberate absence of a capabilities
   table (`authorization.md:378`)? If yes, state the reconciliation
   boundary precisely: Belimbing has **no universal boot-time
   reconciliation and none across principal grants**, while system-role
   seeding is *partially* reconciled (`AuthzRoleCapabilitySeeder` diffs and
   deletes stale mappings for configured system roles). Decide whether
   Bilimbi adds boot-time reconciliation, and of what scope.
