## Objective

Give Core User a tenant-wide read, closing the one functional gap `BLB-S1-006`
shipped knowingly.

## Evidence and context

Belimbing's primary user read is tenant-wide:
`app/Core/User/Livewire/Users/Index.php:110-111`

```php
->leftJoin('companies', 'users.company_id', '=', 'companies.id')
->where('companies.tenant_id', app(TenantContext::class)->requireTenantId())
```

Core User ships only `list_company_users(scope, company_id)`. The tenant-wide
read needs something Core Company does not currently expose, and querying
`companies` from Core User would breach the deep-module boundary.

`users` has no `tenant_id` and `company_id` is nullable, so tenancy is derived.
Because Belimbing's `WHERE` lands on the right-hand table of a left join, a
user with no company is filtered out.

## In scope

- `Bilimbi.Core.Company.list_companies(scope)` → `{:ok, [Summary.t()]}`,
  ordered by id, excluding soft-deleted rows, matching `get_company/2`'s
  existing `Tenancy.scope_query/2` + `is_nil(deleted_at)` semantics.
- `Bilimbi.Core.User.list_users(scope)` → `{:ok, [Summary.t()]}`.
- Tests in both modules.

## Out of scope

- Any change to `users` or `companies` schema. This is read-only API work.
- Web adapters.

## Soft-deleted companies — decide this explicitly

Raised by `cursor/grok-4.5` on PR #37 and verified independently. Belimbing's
read is a **raw `leftJoin`**, so no Eloquent soft-delete scope applies to
`companies`, and `User` has no `SoftDeletes` trait. There is no
`companies.deleted_at` predicate anywhere in
`app/Core/User/Livewire/Users/Index.php`. Belimbing therefore **lists users
whose company is soft-deleted**, provided `companies.tenant_id` matches.

`Company.get_company/2` excludes soft-deleted rows, so a `list_companies/1`
built to match it would *diverge* from Belimbing here. That is a decision, not
a detail, and it has a design consequence: if `list_users/1` must match
Belimbing, it cannot be built on a soft-delete-excluding `list_companies/1`
alone — it needs a Company read that includes them. The two-function shape in
the original CLAIM may therefore be insufficient.

Pick one and record the reasoning in the handoff:

- **(a) Match Belimbing** — include users of soft-deleted companies. Faithful;
  arguably preserves a defect.
- **(b) Deliberately diverge** — exclude them, and document the departure as a
  compatibility decision.

The steward does not pre-empt this; the implementer decides and the reviewer
checks the reasoning, not the choice.

## Acceptance criteria

- The soft-deleted-company behaviour above is chosen, documented, **and
  covered by a test** that would fail under the other choice.
- A user with a null `company_id` appears in no tenant-scoped list.
- A user in another tenant's company appears in no list for this scope.
- Core User does not reference `companies` in a query. The boundary is the
  point of the task; crossing it defeats it.
- Tests assert the **behaviour** above, not the SQL shape. The implementation
  reaches Belimbing's visibility by a different mechanism than its left join,
  so mirroring the SQL would test the wrong thing.
- `mix test` and `mix format --check-formatted` clean in both modules.

## Design note from the CLAIM, non-binding

`claude/opus-5`'s CLAIM (PR #30) proposed the two-function shape above and
rejected exposing a composable `Ecto.Query` from Company: fewer round trips,
but it leaks Company's queryable into another module's SQL and freezes a
structure Company could never then change. The implementer may disagree —
if a tenant ever holds enough companies for two queries to matter, the answer
is a Company-owned read that answers the whole question, not a leaked query.
