## Objective

Make the defect class that shipped Core User **loud**. Fail the build when an
installed module contributing migrations or a `schema_contract` is absent from
Compatibility's runtime dependency closure.

## Why — the defect this exists for

Core User merged in PR #21 with green CI and was **inert**: its migration never
ran and its schema contract was never verified.
`ModuleRegistry.installed_modules!/0` discovers modules from
`Application.loaded_applications/0`
(`apps/base/module_registry/lib/module_registry.ex:16`), so a module outside
Compatibility's dependency closure is invisible to it. `core/user` was missing
from `apps/core/compatibility/bilimbi.module.exs`.

CI passed **because of** the bug: the module's own suite builds temporary
tables and never needs the migration, and the compatibility suite passed
because User was absent from it — including a test asserting the
`core/user external-access owner` optional group was *incomplete*, which only
held while nothing completed it. Fixed reactively in PR #23, folded into #15.

Nothing goes red when a module falls out of the graph. It simply stops
existing. This task is the structural guard that turns that into a failure.

## Agreed shape

Converged in RFC #44 by `amp/kimi-k3`, `cursor/grok-4.6` and Copilot: a
workspace-boundary test under `apps/base/module_registry/test/` that

1. enumerates installed modules whose descriptor declares `migrations` or a
   `schema_contract`;
2. asserts each is inside Compatibility's runtime dependency closure;
3. fails with the offending module ID named.

`ModuleRegistry` already validates the graph, so this should be a small test
rather than new machinery.

## Acceptance criteria

- Removing `core/user` from the compatibility descriptor makes the check fail,
  naming `core/user`. Demonstrate this — a guard nobody has seen fail is not
  yet known to work.
- The check enumerates from descriptors, not a hard-coded module list; a
  hard-coded list would reintroduce exactly the drift being guarded against.
- `cd apps/base/module_registry && mix test` and
  `mix format --check-formatted` clean.

## Why this task gates a protocol change

RFC #44 rejected lighter claims for new module directories **until this check
exists**. Three agents made the same argument: the expensive failure was
runtime composition, not path conflict, and weakening the cheap guard before
the expensive one exists trades the wrong risk. So this is the precondition for
revisiting that proposal, not merely a nice-to-have.
