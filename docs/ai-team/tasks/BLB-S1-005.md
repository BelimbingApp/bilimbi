## Objective

Decide, with evidence, whether Core Employee moves to an optional `people`
Domain now, stays in Core, or has its move deferred past the S1 gate — and
record the decision durably.

## Evidence and context

Observed in the worktree at 2026-08-12T19:34+08, after `BLB-S1-003` was
registered against `apps/core/employee/**`:

- `apps/people/bilimbi.container.exs` declares a new container
  `id: "people", kind: :container, layer: :domain`.
- `apps/people/employee/bilimbi.module.exs` declares
  `id: "people/employee", layer: :domain, required: false`,
  `namespace: Bilimbi.People.Employee`.
- `apps/people/employee/priv/repo/migrations/20260812112641_create_people_employee_compatibility_baseline.exs`
  is the relocated Employee baseline.
- `apps/core/employee/` still exists as an empty `docs/`+`lib/` husk with no
  `bilimbi.module.exs`.

This conflicts with four recorded positions:

1. `AGENTS.md` §2: "Do not add optional Domains or Extensions yet ... deferred
   until Base and Core are stable."
2. `AGENTS.md` §4: Core "owns foundational business modules such as User,
   Company, Employee".
3. `PORTING_STAGES.md` S1 names Employee a Platform Baseline capability and S5
   is where the first optional Domain is introduced.
4. Belimbing canonical ownership is `app/Core/Employee`, migration prefix
   `0200_01_09_*`, between Core Company (`0200_01_07_*`) and Core User
   (`0200_01_20_*`).

The load-bearing consequence is a layer violation, not a preference. In
Belimbing, `users.employee_id` is a real foreign key to `employees`
(`app/Core/User/Database/Migrations/0200_01_20_000000_create_users_table.php:23-25`).
If Employee is a Domain and User is Core, then porting User makes Core depend
on a Domain, which `AGENTS.md` §4 forbids and which descriptor discovery is
specified to reject. `required: false` compounds it: a required Core table
would carry a foreign key into a table whose module may be absent.

Two further defects observed in the relocated module, reported to the owner
and left unedited:

- the descriptor declares `schema_contract: Bilimbi.Core.Employee.SchemaContract`
  while the file defines `Bilimbi.People.Employee.SchemaContract`;
- the empty `apps/core/employee/` husk has no descriptor, and `AGENTS.md` §6
  requires every immediate container child to have a valid one.

## In scope

- Decide Employee's owning layer and stable module ID.
- Decide how `users.employee_id` is satisfied under that choice.
- Record the decision as an ADR and reconcile `AGENTS.md`, `PORTING_STAGES.md`,
  and the descriptor.

## Out of scope

- Editing `apps/people/**` or `apps/core/employee/**`. Both are inside the
  `BLB-S1-003` reservation.
- Porting Core User.

## Acceptance criteria

- The decision names the Belimbing evidence it preserves or deliberately
  departs from.
- No Core module ends up depending on a `:domain`-layer module.
- Either the `people` container is justified against the S1 gate, or it is
  reverted by its owner before the gate is claimed.
- The descriptor/husk defects above are resolved by the owning task.
